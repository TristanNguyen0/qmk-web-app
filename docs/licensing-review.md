# Licensing review — QMK and bundled dependencies

`claude.md` § Build isolation and security names this review a prerequisite to public
deployment: "Establish legal/licensing review for QMK and any bundled
dependencies/assets before public deployment." This document is that review. It
follows the prose conventions of the ADRs in `docs/adr/` — rationale first, full
sentences, no bullet-only shorthand — but it is deliberately not numbered as one: an
ADR records a decision made once; this record will be re-run every time the QMK pin
moves, a new curated module is added, or a new production dependency with an
unfamiliar license is introduced. Its claims are derived from three sources checked
directly rather than from memory: the pinned QMK checkout's own `LICENSE` file, the
curated module registry, and `pnpm licenses list --prod` run against this repository's
actual installed dependency tree. Where a command's output disagreed with an
expectation, the output is what is recorded here.

## 1. What is distributed to a user, and under what licence

The firmware artifact a user downloads is a compiled work built from the pinned QMK
Firmware source tree (`https://github.com/qmk/qmk_firmware.git`, tag `0.33.13`, commit
`332fa30e173e5b0ecc0c70ff166974b6db86525e`, recorded authoritatively in
`infra/qmk/manifest.json`), plus the generated keymap directory this application
writes into that tree per build. The pinned checkout's top-level `LICENSE` file is the
canonical GNU General Public License, Version 2 text; a per-file SPDX survey across
`quantum/` and `tmk_core/` (`grep -rh 'SPDX-License-Identifier'`) finds the identifier
is predominantly `GPL-2.0-or-later`, with a smaller number of files in `tmk_core/`
carrying `GPL-3.0-or-later` or `GPL-3.0-or-later OR Apache-2.0`. The QMK tree also
ships `license_Modified_BSD.md` and `license_GPLv3.md` alongside the top-level GPLv2
text — evidence of QMK's historical mixed per-component licensing (`tmk_core` began
life under a Modified BSD license before parts of it moved to GPL) that this review
did not itemize file-by-file. **The practical conclusion a distributor needs is
unambiguous regardless of that mix: the compiled firmware is a GPL-licensed work**,
because GPL-2.0-or-later is the identifier on the overwhelming majority of the files
that actually compile into a QMK firmware image (`quantum/`, `platforms/`, the
keyboard-specific `.c`/`.h` files), and GPL is viral with respect to the whole linked
program, not diluted by a permissively-licensed minority.

What that means for a user who downloads a firmware image: they are receiving a
GPL-derived binary, and GPL §3 obligates whoever distributes it to also make the
corresponding source available — either accompanying the binary or by written offer.
This application satisfies that by construction rather than by a separate offer
mechanism: the exact source is the pinned commit
(`332fa30e173e5b0ecc0c70ff166974b6db86525e`, publicly fetchable from the upstream URL
above) plus the generated keymap directory, whose entire contents are deterministically
reproduced from the stored configuration revision and the recorded generator version
on the build's own row (`Build.configurationRevision`, `Build.generatorVersion`,
`Build.qmkCommit`) — see `packages/domain/src/build.ts`. Nothing about a given user's
generated keymap is discretionary or undocumented; it can be regenerated byte-for-byte
from data the application already stores and already shows the user owns.

**Open, and the one action item this review produces:** the application does not
currently surface a written notice of these facts (the GPL license, the pinned source
URL/commit, and how to regenerate the exact keymap source) anywhere in the download
response or the UI around it. Corresponding-source availability is satisfied
technically, but GPL compliance is also about *telling the recipient* where it is.
See § Actions below.

## 2. What is redistributed by the repository itself

`catalogs/<version>/` — the published, immutable catalog artifact the API serves
through `listKeyboards`/`getKeyboard` — is derived from the pinned QMK tree's own
`info.json` metadata by QMK's own tooling, per
[ADR 0002](adr/0002-catalog-derives-from-qmk-tooling.md): an in-image Python extractor
using QMK's `lib/python/qmk` API enumerates keyboards and resolves each one's info
JSON with no product-level filtering or repair, and a TypeScript normalizer
(`packages/qmk-catalog`) turns that into the structured, versioned catalog the
frontend renders from. `catalogs/` itself is git-ignored (`.gitignore`: "Generated
catalogs and build workspaces") — it is never committed to this repository's history —
but it is served to every user of the deployed application, which is the redistribution
this question is actually about.

What is in it: per-keyboard facts — canonical id, display name, manufacturer, layouts,
matrix positions, and layout macro names — parsed from QMK's own `info.json` files,
which are themselves data files inside the GPL-licensed QMK tree. Facts alone
(a keyboard's name, its matrix geometry) are not copyrightable subject matter in most
jurisdictions, and republishing normalized facts extracted from a public, GPL-licensed
project's own published hardware descriptions is standard practice among the QMK
ecosystem's own configurator tools (QMK Configurator itself does exactly this against
the same `info.json` files). This review did not find a license notice inside
individual `info.json` files distinguishing them from the surrounding GPL grant, so the
conservative reading is that they carry the same GPL-2.0-or-later grant as the rest of
`quantum/`/`keyboards/` — which, for a *derived, normalized, facts-only* republication
rather than a verbatim copy of the JSON files, does not itself trigger GPL's
source-availability obligation the way distributing compiled/linked code does. **This
is a judgment call this review flags rather than resolves with certainty:** if the
catalog ever moves from "facts extracted and renormalized" toward "the `info.json`
files themselves, verbatim," attribution and source-availability treatment should be
revisited.

## 3. The community module (SOCD Cleaner)

`MODULE_REGISTRY['qmkweb/socd_cleaner']` (`packages/domain/src/module-registry.ts`)
records this module's license as `GPL-2.0-or-later`, matching the `license` field in
its own `qmk_module.json`
(`packages/qmk-socd-module/module/qmkweb/socd_cleaner/qmk_module.json`). Per
[ADR 0005](adr/0005-socd-is-a-first-party-community-module.md), it is carried as
digested, first-party C source under `packages/qmk-socd-module` — `sourceRevision`
records `moduleVersion: '1.0.0'`, `firstParty: true`, and the three files that
constitute it (`qmk_module.json`, `socd_cleaner.c`, `socd_resolve.h`) — rather than
fetched from a third-party repository at build time. It is GPL-2.0-or-later,
consistent with the QMK core code it is compiled and linked alongside, so it
contributes no additional licensing question beyond what § 1 already covers for the
firmware as a whole: it is part of the same GPL-derived compiled work, and its own
source (already inside this repository, not an external fetch) is exactly as available
as this repository's own history.

## 4. Bundled runtime dependencies

`pnpm licenses list --prod` against this repository's installed production dependency
tree finds seven distinct license identifiers:
`0BSD`, `Apache-2.0`, `BSD-3-Clause`, `CC-BY-4.0`, `ISC`, `LGPL-3.0-or-later`, `MIT`.
Six of the seven — `0BSD`, `Apache-2.0`, `BSD-3-Clause`, `CC-BY-4.0`, `ISC`, `MIT` — are
permissive licenses with no obligation beyond attribution/notice preservation, which is
already satisfied by leaving each package's own `LICENSE`/`package.json` intact inside
`node_modules` as installed; none of them creates an obligation this project is not
already meeting.

The one that needed a closer look is `LGPL-3.0-or-later`, carried by exactly one
package: `@img/sharp-libvips-linux-x64`, a prebuilt native `libvips` shared library
distributed as a platform-specific binary for the `sharp` image-processing library
(itself an optional dependency of Next.js's built-in image optimization, not code this
project imports directly). LGPL's central obligation — that a user be able to relink
the work against a modified version of the LGPL component — is satisfied by the
architecture here without any extra step: `sharp` loads `libvips` as a dynamically
linked native addon (a `.node`/shared-library boundary, not statically compiled into
this application's own JavaScript), which is exactly the dynamic-linking case LGPL
§4/§6 (v3) treats as already satisfying the relinking requirement. **No action is
required for this dependency**, but its presence is worth naming explicitly rather than
silently passing it in the "permissive" bucket it is not actually in.

This survey covers `--prod` (what actually ships/runs), not `devDependencies` — the
test runner, linter, and build tooling are never distributed to a user, so their
licenses do not attach to anything this application redistributes.

## Actions

1. Add a licence/source notice around the firmware download response or the UI
   surrounding it, stating: the firmware is GPL-2.0-or-later derived, naming the
   pinned upstream URL and commit, and pointing to how the exact generated keymap
   source is reconstructed from the configuration revision, catalog version, QMK
   commit, and generator version already recorded on the build. This closes the one
   open item from § 1 — corresponding source is technically available today, but is
   not yet *announced* anywhere a downloading user would see it.

No other action is required by this review as of the pin and dependency tree it was
run against.

## Re-run trigger

Re-run this review whenever any of the following happens: the QMK pin in
`infra/qmk/manifest.json` moves (a new tag/commit is a new catalog version and a new
build image per `claude.md` rule 6 and [ADR 0001](adr/0001-technology-stack.md) — its
license identifiers are not guaranteed to hold across an upstream release); a new
curated module is added to `MODULE_REGISTRY`; or a new production dependency is
introduced whose license identifier does not already appear in § 4's list above.
