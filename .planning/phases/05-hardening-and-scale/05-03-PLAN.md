<objective>
Make anonymous-only a decision the product states rather than a gap it has.

**D-01** takes criterion 5's second branch deliberately: accounts are not built, and anonymous-only
is a recorded launch constraint. That is only defensible if the constraint is visible where it
bites and if a user has a way out. **D-02** makes it visible with a persistent, non-dismissable
line — dismissable was rejected because the dismissal would live in the very cookie that is at
risk, so the user most likely to be harmed is the one who would never see the notice again.
**D-03** provides the way out: export a configuration as JSON, and import one back into the
current session as a new configuration.

The import is explicitly **not** a new trust boundary. It reuses `POST /v1/configurations`, the
same `asInput` field allowlist, and the same `validateConfiguration` call every other write takes.
No new endpoint is added, so there is no second door to audit.

Purpose: criterion 5 of the phase.
Output: a versioned export envelope with a strict parser, two client controls, one persistent
notice on two surfaces, and ADR 0006 recording the decision.

**Sequencing note:** this plan declares `depends_on: ["05-01"]` for tracer-first ordering,
not for a code dependency — none of its files overlap 05-01's. The phase leads with one
production-quality end-to-end slice (the atomic build-admission path) and proves it against
real Postgres before four plans build on this codebase in parallel.
</objective>

## Premise correction: D-05's stated rationale is factually wrong

CONTEXT.md D-05 declines a UI contract on the ground that "`apps/web` already carries the
patterns" — meaning Tailwind and Radix. **It does not.** `apps/web/package.json` declares neither;
there is no `tailwind.config.*` anywhere in the app; and `apps/web/src/app/globals.css` opens by
stating that plain CSS was chosen deliberately for Phase 1 and that pulling Tailwind and Radix in
before there was an editor to style would be premature. That premise was never revisited through
Phases 2-4: `KeymapEditor.tsx` still renders with hand-written class names against a 628-line
plain CSS file.

**The conclusion still stands; only the reasoning changes.** No UI contract is needed, because a
status line and a download/upload control are conventional and this app has an established,
consistent convention to follow — it is simply the plain-CSS `.provenance` / `.notice` convention
rather than a component library. Introducing Tailwind or Radix mid-phase for two small controls
would be new dependency surface D-05 did not intend to authorise, and RESEARCH.md's Anti-Patterns
section rejects it explicitly. This plan is written against the actual convention.

## Which CSS class

PATTERNS.md is specific and this plan follows it: extend `.provenance` (a permanent, factual
disclosure already used on the configurations list page), not `.notice`. `.notice` is used across
`BuildPanel.tsx`, `KeymapEditor.tsx`, `MacroEditor.tsx`, `CreateConfigurationButton.tsx` and
`SocdPanel.tsx` for transient and error states; reusing it for a permanent line would teach users
that the permanent line is something that goes away.

The edge probe classified one `REQ-launch-identity-model` row as `unclassified`, and per protocol
it stays **unresolved** rather than being auto-resolved with a backstop. It is surfaced here as a

<assumption_delta_decision>
**Signal.** The assumption-delta detector fired on a pluralization in criterion 5 — "a user can
reach their configurations from a **second** device". The question that raises: does `ownerId`
still name the right noun, now that D-01 has taken the anonymous-only branch?

**The noun that is now primary.** Still the **owner** — the authorization subject. Criterion 5's
first branch would have made "account" or "person" primary and introduced a one-to-many
relationship between that noun and a session. D-01 declines that branch, so no new noun becomes
primary in this phase.

**Decision: `no-change`.** `ownerId` already names the authorization subject abstractly rather
than naming a session. What would change when accounts arrive is only what gets *assigned* to
`ownerId` inside the session hook — a session UUID today, an account id later — which is exactly
the "only the identity source changes" boundary `ADR-0001-auth` draws. Introducing a second noun
now would either duplicate `ownerId` in every SQL predicate or force a rename across every
`WHERE owner_id = $1` in the tree, for no present benefit, and against a decision that
deliberately deferred accounts.

**What would force a later `add-alongside`.** If one owner ever needs to hold more than one
identity credential at the same time — a cookie session and an account, or two devices being
merged — the move is a new `identities(owner_id, source, external_id)` table alongside the
existing `configurations.owner_id` and `builds.owner_id`, never a second owner column on those
tables. `ownerId` stays the subject; the identities table becomes the source.

**Suggested invariant test (for 05-05, which owns `apps/api/src/session.ts`).** A test in
`apps/api/src/session.test.ts` asserting that `request.ownerId` is assigned in exactly one place:
scan `apps/api/src` for assignments to the `ownerId` request property and assert the only match is
in `session.ts`. It goes red the moment a future phase reintroduces a second identity source
inline instead of routing it through the one hook — which is the concrete way the singular
assumption would come back.
</assumption_delta_decision>
