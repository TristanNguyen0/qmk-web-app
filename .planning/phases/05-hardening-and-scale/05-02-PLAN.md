<objective>
Turn two duplicated one-off scripts into one curated smoke matrix with written membership
criteria, so "catalogued" and "known to build" stop being the same claim.

`services/worker/scripts/smoke-build.ts` and `services/worker/scripts/socd-compile-matrix.ts`
already run the identical pipeline — open the published catalog, build a configuration input,
validate, generate, `DockerSandbox`, `runBuild`, assert firmware. **D-07** extracts that into one
runner parameterised by a fixture set. **D-08** widens membership by toolchain and bootloader
diversity using the pinned catalog's own `processor`/`bootloader` data. **D-10** keeps exactly
one designated entry building twice and asserting byte-identical output.

The load-bearing invariant is the guard at `socd-compile-matrix.ts:163-175`: every keyboard the
registry records as compile-verified for this catalog version must have a fixture. That guard is
the evidence behind every `verifiedFor` record, and a refactor that loses it silently weakens a
shipped claim. This plan makes it a unit-tested pure function so it can never be lost silently.

Purpose: criterion 3 of the phase — the matrix that 05-06 turns into a merge gate.
Output: `run-matrix.ts`, two fixture sets, a `pnpm matrix` entry point, `docs/matrix-selection.md`,
and a real matrix run recorded in the SUMMARY.

**Sequencing note:** this plan declares `depends_on: ["05-01"]` for tracer-first ordering,
not for a code dependency — none of its files overlap 05-01's. The phase leads with one
production-quality end-to-end slice (the atomic build-admission path) and proves it against
real Postgres before four plans build on this codebase in parallel.
</objective>

## Premise correction and discretion decisions recorded here

**Correction to CONTEXT.md and RESEARCH.md.** Both state that `smoke-build.ts` "already builds
twice asserting byte-identical firmware." It does not. Lines 155-165 of that file *report* the
comparison and explicitly decline to assert: *"Not necessarily a defect: the keymap directory
name differs per build id, and QMK may embed build metadata. Report it precisely rather than
asserting."* D-10 requires an assertion, so this plan changes the shape of the check, and the
change is deliberate rather than a transcription of existing behaviour.

The way to make it a sound assertion is to hold the build id constant across the two builds.
`generatedKeymapName(buildId)` derives the keymap directory name from the build id, so two
different build ids legitimately produce two different firmware images — that is not a
determinism failure, and asserting across differing ids would be asserting the wrong thing.
D-10's own words are that "determinism is a property of the generator and the pinned image,"
which is exactly what a same-build-id double build isolates. `runBuild` allocates a fresh
`mkdtemp` workspace per call, so re-using an id is safe.

**Discretion — matrix membership and size cap (RESEARCH.md § Open Questions 2).** Selection is
by `(processor, bootloader)` coverage weighted by how many supported keyboards share each pair —
a count the pinned catalog carries, unlike popularity, which it does not. Five members, size cap
eight. `handwired/onekey/*` is QMK's own single-key per-MCU probe board (`LAYOUT_ortho_1x1`,
one position), which makes an added toolchain cost one short compile instead of a hand-written
key table. Full criteria and arithmetic go into `docs/matrix-selection.md` in Task 3.

**Discretion — whether the catalog build belongs in CI.** No. The catalog is an immutable
versioned artifact produced by an offline administrative pipeline (ADR 0002), and rebuilding it
per run would produce a *new* catalog version, which `ADR-0001-qmk-pin` forbids as an in-place
mutation. The matrix consumes the published `catalogs/0.33.13-1/` directory.

**Discretion — quarantining a failing matrix entry.** No quarantine mechanism. A quarantine list
is precisely the "catalogued versus known to build" blur `REQ-smoke-matrix` exists to remove. A
fixture that stops compiling is either a real regression to fix, or a keyboard that leaves the
matrix through an explicit, reviewable commit that also removes any registry claim resting on it.
</planner_notes>
