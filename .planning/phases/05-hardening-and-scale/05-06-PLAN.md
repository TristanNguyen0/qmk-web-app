<objective>
Turn the curated matrix from a script someone might remember to run into a merge gate that is
literally blocking.

`claude.md` § Testing strategy is unambiguous: *"No pull request that changes generator, QMK pin,
templates, or build image should merge without compiling the curated smoke matrix."* This
repository has no CI at all — `.github/workflows/` does not exist — so that sentence has never
been enforced by anything but discipline.

**D-06** puts the gate on a self-hosted runner on the build host, because that machine already
holds Docker, the pinned 3.73 GB build image and the pinned QMK checkout, so a run costs the
compiles and nothing else. It also records a hard constraint: **the self-hosted runner must never
execute fork pull requests.** **D-09** path-filters the expensive job and names the sharp edge to
handle deliberately — a required check that a path filter skips never reports, and blocks the
pull request forever.

Purpose: criterion 3 of the phase, plus the dependency and image scanning half of
`REQ-backup-retention-controls`.
Output: the repository's first two workflows, a runner runbook, and a gate proven to block on a
real pull request.
</objective>

<planner_notes>
## Decisions made here

**Both workflows run on the self-hosted runner.** D-06 only requires it for the matrix, but the
fast check runs there too. The reason is not cost: it is that the runner is the environment whose
Node and pnpm versions actually build firmware, and introducing a second execution environment
with different versions would mean a green fast check proves something about a machine no
artifact is ever produced on. The tradeoff is real and goes in the runbook — when the runner is
offline, neither required check reports and nothing merges. `runs-on` is written in exactly one
place per workflow so moving the fast check to a hosted runner later is a one-line change.

**No third-party marketplace actions on the self-hosted runner.** Changed-path detection uses an
inline `git diff` rather than a path-filter action, and Trivy runs from its own container image
pinned by digest rather than from a marketplace action. A self-hosted runner is the single worst
place to grant a third-party action the runner's filesystem and Docker socket — which is the same
reasoning behind D-06's fork-PR constraint, applied to the other supply-chain direction. Only
`actions/checkout` is used, and it is version-pinned.

**A fork pull request must FAIL the gate, not skip it.** Pattern 5's job-level guard stops the
job running, but a required check satisfied by a *skipped* job would mean opening a pull request
from a fork is a way to bypass the matrix entirely. So the aggregating job fails explicitly when
the head repository differs from the base repository, with a message saying so. The gate's
meaning is "the matrix compiled or was genuinely not applicable" — a fork is neither.

**Scanning gates on fixable findings only.** Trivy runs with unfixed vulnerabilities ignored and
gates on high and critical. A 3.7 GB toolchain image will always carry unfixable OS findings; a
gate that is permanently red is a gate that gets disabled, which is strictly worse than a gate
scoped to what can actually be acted on. The full unfiltered report is still printed, so nothing
is hidden — only the exit code is scoped.

**The scanning job is not path-filtered.** A dependency's vulnerability appears without anyone
touching a dependency file, so it runs on every pull request alongside the fast check, and the
image scan runs whenever the matrix job runs.
</planner_notes>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| pull-request author → self-hosted runner | Workflow-defined code executes on a machine holding the Docker socket, the pinned QMK checkout and the build image |
| marketplace action → runner | A third-party action runs with the runner's full privileges |
| branch protection → `main` | The only mechanical thing standing between an unverified generator change and the default branch |
