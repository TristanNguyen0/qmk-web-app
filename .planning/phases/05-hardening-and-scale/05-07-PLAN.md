<objective>
Make the service operable by someone who is not watching its console.

`ADR-0001-observability` set a two-stage plan: structured JSON logs now, OpenTelemetry-compatible
exporters before public access. This phase is the "before public access" trigger. The worker
already emits one-line structured JSON per event; nothing exports a metric, and no
`@opentelemetry/*` package exists anywhere in the dependency tree.

Criterion 2 names four signals: queue depth, build throughput, failure classification and worker
liveness. All four are metrics, and this plan exports them over OTLP. The collector is
deliberately not chosen here — `ADR-0001-observability` makes it a deployment concern to avoid
premature vendor lock-in, and with the endpoint unset the whole telemetry layer is inert.

The load-bearing constraint is the second half of that ADR: **log redaction rules apply to every
sink added later.** A new sink does not inherit redaction automatically, because redaction is
currently a function called at one call site rather than a property of a shared abstraction. This
plan closes that two ways — an attribute allowlist that makes free text impossible by
construction, and the existing redaction tables applied to what remains.

Purpose: criterion 2 of the phase.
Output: a metrics bootstrap in both processes, four instruments, an attribute allowlist, and a
documented query set.
</objective>

<planner_notes>
## Deviation from RESEARCH.md's package list, with reasoning

RESEARCH.md § Standard Stack proposes six OpenTelemetry packages including
`@opentelemetry/sdk-node` and `@opentelemetry/exporter-trace-otlp-proto`. **This plan installs
four and drops those two.**

Criterion 2 names four signals and every one of them is a metric. `sdk-node` exists to wire
tracing and auto-instrumentation, neither of which criterion 2 asks for — and it carries the
constraint RESEARCH.md itself quotes: *"the SDK must be initialized before any other module in
your application is loaded."* Honouring that in ES modules means a preload wrapper on both
process entry points, because `import` statements hoist above any `start()` call written inside
the entry file. That is a real operational constraint on `pnpm dev`, on the worker's start
command, and on anyone running either process by hand — accepted for zero gain against the
requirement, since manual metric instruments do not need the process instrumented before load.

So: `@opentelemetry/api`, `@opentelemetry/sdk-metrics`,
`@opentelemetry/exporter-metrics-otlp-proto` and `@opentelemetry/resources`. Traces remain an
additive next step behind the same bootstrap module, and the runbook records what adding them
would require. Record this deviation in the SUMMARY so a later reader does not treat it as an
oversight.

## Why the redaction story is split in two

`services/worker/src/redact.ts` lives in the worker package, and the API must not import worker
code — that dependency direction would be wrong and would drag the sandbox and build machinery
into the API's graph. Moving redaction into a shared package is a refactor this phase does not
need.

Instead the guarantee is met by the strongest available means on each side. In the API, the
attribute builder is an **allowlist**: it accepts only enumerated keys carrying enumerated string
values or numbers, and throws on anything else, so free text cannot reach the sink at all — there
is nothing to redact because nothing textual is admitted. In the worker, the same allowlist
applies **and** the existing redaction tables run over the surviving string values, because the
worker is the process that actually holds build-log text and container paths.

An allowlist is a stronger guarantee than a redaction pass — a regex table can miss a novel
secret shape, whereas a key that is not in the list is simply not exported. Say so in the module
header, so a later author does not "simplify" the allowlist away in favour of redaction alone.

## Discretion: no dashboard ships

CONTEXT.md leaves this to the planner. Criterion 2 says an operator *can see* the four signals,
which exported signals plus a documented query set satisfy. Shipping a dashboard would mean
choosing a backend, which is exactly what `ADR-0001-observability` defers. `docs/runbooks/observability.md`
carries the queries instead.
