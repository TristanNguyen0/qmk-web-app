<objective>
Make build admission a single, race-free decision the database owns.

Today `assertWithinQuota` reads two counts in `apps/api/src/builds/service.ts:120-140`, throws
if either is over, and then `repository.create()` inserts in a separate round trip. Between the
read and the insert there is a window; with more than one API process there is no window at all
because there is no shared state. There is also no global cap of any kind, so any number of
fresh anonymous sessions can each stay inside their per-owner allowance and still bury the
single build host (`README.md` § Known gaps).

This plan replaces that with one admitting transaction that holds a transaction-scoped advisory
lock, counts global-active / owner-active / owner-hourly, and inserts only if all three pass —
implementing **D-11** (global queue-depth cap enforced in the insert path) and **D-13** (both
per-owner checks folded into the same decision). It is the phase's tracer: the thinnest real
path from `packages/domain` through `packages/build-queue` and `apps/api` to an HTTP 429,
proven under real concurrency before any other Phase 5 work builds on this codebase.

Purpose: criterion 1 of the phase — "a burst of build requests … is absorbed by a global
concurrency limit and queue backpressure, returning `BUILD_QUEUE_LIMITED` instead of saturating
the single host."
Output: a three-predicate atomic admission path, a `rejected` outcome that names the cap that
bit, and contract tests that fail if the race ever returns.
</objective>

## Premise corrections and discretion decisions recorded here

**Discretion — the global cap's value (RESEARCH.md § Open Questions 1).** `maxGlobalActiveBuilds`
is set to **8**. Reasoning, to be written into `limits.ts` in the same comment style as its
neighbours: the host runs one worker, which compiles one build at a time, so queue depth is
directly a wait time — depth × mean compile time ÷ worker count. At ~60-120 s per compile, a
depth of 8 is a worst case of roughly 8-16 minutes for the last person in line, which is the
edge of tolerable. 8 is also 4× `maxActiveBuildsPerOwner`, so four distinct sessions can each
hold their full allowance before the global cap bites. **Tuning trigger:** raise it when more
than one worker runs, in proportion to worker count — not in response to a single busy hour.

**Correction to RESEARCH.md Pattern 1.** Pattern 1 puts the cap predicates inside the `INSERT`
and then says the caller "must re-read the `counts` values … to build a specific, user-safe
message". Those two requirements cannot both be met by one statement: `RETURNING *` yields
nothing on a `WHERE`-rejected `INSERT ... SELECT`, so the observed counts are gone. This plan
does **both** halves inside one advisory-locked transaction: read the counts (safe, because the
lock serialises the region), branch in TypeScript to name the cap, and *also* keep the three
predicates on the `INSERT` so the database remains the final authority. The predicates are not
redundant decoration — they are what makes the guarantee independent of the application code
path, which is D-11's actual requirement.

**Correction to RESEARCH.md Pattern 1, second half.** Pattern 1's shape would reject an
idempotent replay from an owner who is now at their cap, turning a retry into a 429 and
breaking `ADR-0004-idempotency`. The existing-key lookup must therefore happen **before** the
caps are consulted, inside the same locked transaction.
</planner_notes>

| browser → `POST /v1/configurations/:id/builds` | Untrusted, unauthenticated-beyond-a-cookie input requests the most expensive operation the system performs |
