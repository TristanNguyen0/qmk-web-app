<objective>
Make retention accountable and make a restore a thing that has actually been done.

`QueueRunner.maintain()` today reclaims leases, reaps expired artifact rows and log references,
deletes the blobs, and — when at least one blob delete succeeded — logs a one-line summary of
counts. Nothing records *what* was deleted, and if every blob delete fails the sweep is entirely
silent. Criterion 4 asks an operator to "state what retention actually deleted and when," which
that cannot answer.

This plan adds a durable retention record, ships `pg_dump`-based backups with a restore drill
that runs for real against a scratch database, and writes the licensing review `claude.md`
§ Build isolation and security names as a prerequisite to public deployment.

Purpose: criterion 4 of the phase.
Output: a retention record in the worker's existing structured-event shape, two scripts, and two
documents.

**Sequencing note:** this plan declares `depends_on: ["05-01"]` for tracer-first ordering,
not for a code dependency — none of its files overlap 05-01's. The phase leads with one
production-quality end-to-end slice (the atomic build-admission path) and proves it against
real Postgres before four plans build on this codebase in parallel.
</objective>

<planner_notes>
## Discretion decisions recorded here

These come from CONTEXT.md § Claude's Discretion, which the user chose not to discuss. The
defaults recorded there are adopted, with the reasoning made concrete.

**Backups: Postgres only, artifacts never.** Adopted as recorded. Artifacts are seven-day
ephemeral by policy (`BUILD_LIMITS.artifactRetentionMs`) and deterministically reproducible from
a stored configuration revision plus the pinned catalog version, QMK commit, generator version
and build image digest — every one of which is already recorded on the build row. That is exactly
the property the Phase 0 reproducibility spike proved. Backing them up would duplicate a rebuild's
job and buy no durability guarantee a rebuild does not already provide.

**Retention record: structured log events, not a Postgres table.** RESEARCH.md § Open Questions 3
leaves this open and recommends starting with the log event. Adopted, for a reason the research
did not state: `apps/api/migrations/003_worker_role.sql` deliberately gives `qwa_worker` no
`INSERT` anywhere except `artifacts`, and its own comment notes that the retention reaper runs
with owner credentials. A `retention_events` table would need a new grant on a role whose whole
design is a short grant list, for data that a log sink — one this same phase makes exportable
via 05-07 — already carries.

**The trigger for revisiting it, which must be written into the runbook:** add a
`retention_events` table when an operator cannot answer "what did retention delete last month"
from the log sink, which will be true the moment the sink's retention window is shorter than that
question's horizon. That is a deployment fact, not a code fact, so the runbook is where it belongs.

**Scanning is not here.** Dependency and image vulnerability scanning is the other half of
`REQ-backup-retention-controls`, and it lands in 05-06 as a CI job on the same runner as the
matrix, because that is the only machine that holds the build image.
</planner_notes>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| worker → object store | The retention sweep deletes user data; the record of what it deleted is the only account of it |
| database → backup file on disk | A dump carries every session's configurations out of the database's access controls |
| storage key read back from the database → path | A key round-trips through the database before being parsed |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-16 | Repudiation | `QueueRunner.maintain()` deleting without a record | high | mitigate | A retention record conditioned on what was reaped, not on how many blobs were deleted, so a sweep whose deletes all fail is still accounted for; proven by a test that fails against the current implementation (Task 1) |
| T-05-17 | Information Disclosure | storage keys in an operator-facing record | medium | mitigate | The record names build ids only; `buildIdFromKey` converts, and a test asserts the emitted event contains no key-shaped substring (Task 1) |
| T-05-18 | Tampering | a malformed storage key parsed as a path segment | medium | mitigate | `buildIdFromKey` validates the extracted segment with the module's existing build-id assertion and returns null rather than a partially-trusted value (Task 1) |
| T-05-19 | Information Disclosure | backup archives on disk | high | mitigate | The backup directory is created with restrictive permissions, `var/backups` is gitignored, and the runbook states plainly that a dump contains every session's configurations (Task 2) |
| T-05-20 | Tampering | the restore drill writing to the live database | high | mitigate | The drill creates and drops a scratch database only, uses a read-only query path against the source, and states the constraint in its header; the trap-based cleanup is asserted by a deliberate-failure acceptance criterion (Task 2) |
| T-05-21 | Denial of Service | a backup run starving the build host | low | accept | `pg_dump` takes a single transaction snapshot and this database holds configurations and build rows, not artifacts; on a single-host deployment the operator schedules it, and the runbook says to schedule it away from expected build load |
</threat_model>
