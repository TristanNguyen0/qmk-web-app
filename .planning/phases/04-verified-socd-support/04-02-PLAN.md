<objective>
Consolidate the curated module registry into one typed structure and make SOCD availability a
function of the `(catalogVersion, qmkCommit, keyboardId)` triple rather than a flat keyboard set.

Purpose: `REQ-curated-module-registry` asks for an *entry* with seven pinned fields. Today that
metadata is scattered across `qmk_module.json`, `socd.ts`, the digest manifest and ADR 0005, and the
API route computes a catalog version and then discards it. Closing both gaps is what makes
`REQ-socd-policy-choices` clause 7 — "mark it unavailable for that catalog version" — structural
instead of procedural, and gives a second curated module something to extend.

Output: `packages/domain/src/module-registry.ts` as the single source of curated-module truth, a
catalog-version-aware capability function and validator that read it, an API route that passes the
version it already resolved, and the two SOCD panel copy fixes the UI contract requires.
</objective>

<assumption_delta_decision>
The assumption-delta detector fired (`pluralization`, `chosen`) on this phase's scope, and this plan
is where the delta is real: a singular assumption is losing its monopoly.

- **The noun that is now primary:** a *curated-module verification record* — the tuple
  `(moduleId, catalogVersion, qmkCommit, keyboardId, verificationStrength)`. It replaces the old
  primary noun, "a keyboard SOCD has been compiled for", which was modelled as a flat
  `ReadonlySet<string>` of keyboard ids with no module, catalog, commit, or strength dimension.
- **Decision: `promote`.** `MODULE_REGISTRY` becomes primary; the flat keyboard set is demoted to a
  derived view computed from the registry for a given `(catalogVersion, qmkCommit)`, and is no
  longer an independently maintained constant. Rationale: D-01 requires the seven fields to live in
  one entry read by the capability function, and D-10 requires two distinguishable strengths of
  claim, neither of which the flat set can express. Adding the registry alongside a still-primary
  flat set would let the two disagree — exactly the drift the project's cross-checked-table
  discipline exists to prevent.
- **Invariant test (accepted, implemented in Task 1):** availability is a pure function of the
  registry — for every record in `verifiedFor`, `socdCapabilitiesFor(record.catalogVersion,
  record.keyboardId)` reports available, and for any keyboard/catalog-version pair with no record it
  reports unavailable with a reason. This goes red the instant a future phase reintroduces a second,
  independently maintained verified-keyboard list.
</assumption_delta_decision>
