# Phase 4 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Scope note — this is reconciliation, not greenfield

Per `04-CONTEXT.md` and `04-RESEARCH.md`, a complete `SocdPanel.tsx` implementation already
ships on branch `worktree-phase-4-socd` @ `683270f`
(`.claude/worktrees/phase-4-socd/apps/web/src/components/SocdPanel.tsx`). This contract
**documents the visual language that component already honours** — the plain-CSS design
system shipped in Phases 1–3 — and is prescriptive only about the two concrete UI gaps
`04-RESEARCH.md` identified (mod-tap copy, `CAPABILITY_UNAVAILABLE` as a first-class state),
plus one additional visual-consistency gap this research found while reading the panel
(the "could not load capabilities" branch does not use the sitewide `.notice` treatment).
Do not restyle `SocdPanel.tsx`, do not introduce a component library, and do not add spacing
or typography values beyond what is already established — the existing rules already satisfy
every requirement this phase adds.

## Design System

| Property | Value |
|----------|-------|
| Tool | none — hand-rolled CSS custom properties (`apps/web/src/app/globals.css`) |
| Preset | not applicable |
| Component library | none — semantic HTML + ARIA (`<fieldset>`/`<legend>`, `role="alert"` on transient client errors, `aria-labelledby` + `useId()` on sections) |
| Icon library | none — text-only labels everywhere in `apps/web`; do not introduce icons for this phase |
| Font | `system-ui, -apple-system, "Segoe UI", sans-serif`; body set at `16px/1.5` on `<body>` (`globals.css` line 42) |

**Why no shadcn gate was run:** `components.json` is absent, and the stack is Next.js/React
(`apps/web/package.json`: `next ^16.3.0`, `react ^19.0.0`), which would normally trigger the
shadcn initialization gate. It is deliberately skipped here: ADR 0001 already records "Tailwind
CSS + headless primitives (Radix)" as the long-term styling decision, but Phases 1–3 shipped
without adopting it, building instead a deliberate, accessibility-documented plain-CSS system
(`globals.css` line 1: *"Deliberately plain CSS for Phase 1... pulling [Tailwind/Radix] in
before there is an editor to style would be premature."*). Phase 4 is reconciliation of an
already-complete branch that continues that same plain-CSS pattern. Introducing shadcn now
would fork the design system mid-reconciliation and is out of this phase's boundary (not named
in any of the CONTEXT.md decisions or discretion items). If the project wants to act on ADR
0001's Tailwind/Radix decision, that is a separate, explicit phase-scoped decision — not a
side effect of this UI-SPEC.

---

**Visual anchor (focal point).** The panel's focal point is the `Enable SOCD resolution` checkbox —
it is the first control in the fieldset, it gates every other control below it, and nothing else in
the panel competes for attention (no accent color, no icons, no pill). When SOCD is unavailable, the
`.notice` block becomes the focal point instead, because the checkbox is not rendered at all. Do not
introduce a competing emphasis treatment for the policy select or the position selects.

## Spacing Scale

**This phase requires zero new spacing values.** Both required UI changes (the mod-tap
sentence, and treating `CAPABILITY_UNAVAILABLE` as first-class) are copy and class-name
changes onto already-styled elements (`.socd`, `.socd fieldset`, `.notice`). The table below
documents the existing scale for reference and for any future extension of this panel — it is
not new work for this phase.

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px (0.25rem) | Smallest gaps; pill vertical padding (`.unsupported-badge`, `.build-status`) |
| sm | 8px (0.5rem) | `.socd__policy`/`.socd__position` margin-bottom; badge horizontal padding |
| md | 16px (1rem) | `.socd fieldset` / `.socd` top padding; `.notice` padding |
| lg | 24px | Not used inside `SocdPanel`; reserved for section-level padding elsewhere in the app |
| xl | 32px (2rem) | `.socd` margin-top (separation from the layer editor above it) |

The scale above (4 / 8 / 16 / 24 / 32) is the sanctioned scale. This phase adds nothing to it.

> **Known legacy exceptions — NOT part of the scale, do not replicate.** Three shipped rules use
> values that are not multiples of 4. They are recorded here so a future reader does not mistake
> them for sanctioned steps. Do not copy them into new rules, and do not "fix" them in this phase —
> that is an unrelated restyle outside this phase's boundary.
>
> - `.socd legend` — `0.375rem` (6px) horizontal padding
> - `.notice` — `0.875rem 1rem` (14px/16px) padding
> - `.unsupported-badge` — `0.125rem 0.5rem` (2px/8px) padding

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 | 1.5 |
| Label (badge/pill) | 12px | 600 | 1.4 |
| Heading | 18px | 700 (browser default `<h2>` bold) | 1.2 |
| Display | not used | — | — |

Grounding: `body { font: 16px/1.5 ... }` and `h2 { font-size: 1.125rem }` (`globals.css`).
`.unsupported-badge` / `.build-status` establish the 12px/600 label pattern used for
pill-shaped status text; `SocdPanel.tsx` does not currently use a pill for its own state (see
"Copywriting Contract" below for why it should keep using `.notice`, not a badge). No display-
sized text exists anywhere in `apps/web`; do not introduce one for this phase.

**Two weights only, for anything this phase touches:** 400 (regular body/paragraph text,
including the new mod-tap sentence and the updated unavailable-reason copy) and 700 (`<strong>`
emphasis leads, e.g. `<strong>SOCD is not available for this keyboard.</strong>`,
`<strong>Your responsibility:</strong>`). The existing `.socd legend { font-weight: 600 }` is a
pre-existing exception outside this phase's two required changes — leave it unchanged, do not
introduce new 600-weight text.

keyboard SVG, and the active tab/pill states in `.layout-tab`, `.picker__tab`, `.picker__key`.

"enable SOCD" checkbox and radio/select controls render through global unstyled form-control
rules, not accent-colored controls, and this phase does not change that.

There is no separate "destructive" (delete-confirmation) color in this app; the warn triple
above is this app's single second semantic color, used for both errors and product-level
unavailability. That is sufficient for Phase 4 — it introduces no delete/destroy action.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | No new CTA button this phase. Entry point is the existing `Enable SOCD resolution` checkbox label (unchanged); the terminal CTA remains `Build firmware` (`BuildPanel.tsx`, Phase 3, unchanged). |
| Empty state heading/body | Not applicable — `SocdPanel` has no list/collection element. The two states below are the panel's equivalent "nothing to show normally" states. |
| Error state — capabilities failed to load | **Fix required:** change `<p className="muted">Could not load SOCD capabilities for this keyboard.</p>` to `<p className="notice">Could not load SOCD capabilities for this keyboard.</p>` (drop `.muted`, add `.notice`; no `role="alert"`). This is a render-time data-load failure supplied as a prop before render (same shape as `capabilities`/`positions`/`keycodes` elsewhere in `KeymapEditorProps`), so it must match the sitewide **render-time** failure convention — `.notice`, no `role="alert"` — exactly as `apps/web/src/app/configurations/page.tsx:30` (`Could not load your configurations. Is the API running?`) and the keyboard-detail unsupported-keyboard notice already do. Do **not** copy `BuildPanel.tsx`'s `role="alert"` pattern here — that pattern is reserved for transient, client-triggered failures injected after the page has already rendered (e.g. a failed build request), which this is not. |
| Error state — `CAPABILITY_UNAVAILABLE` (success criterion 2) | Keep the existing shape — `.notice`, no `role="alert"` (matches the Phase 1 "Unsupported keyboard" convention, a persistent product state, not a transient one) — but update the reason string to name the catalog version once `socdCapabilitiesFor` gains the `catalogVersion` parameter (D-02): `"SOCD has not been compile-verified for this keyboard on catalog version {catalogVersion} yet. It is enabled only for keyboard/catalog-version combinations that have been through the SOCD compile matrix."` This keeps clause 7 of `REQ-socd-policy-choices` honest — the message must not read as a permanent verdict once a QMK pin bump can change it. |
| Destructive confirmation | None. Disabling SOCD (unchecking the checkbox) calls `onChange(null)` immediately, with no confirm dialog — this matches the established sitewide pattern (macro `Delete`/`Remove` buttons in `MacroEditor.tsx` also act immediately, with no confirmation, relying on the editor's undo/redo per `REQ-visual-keymap-editor`). Do not add a confirmation step; that would be new UI, not a gap this phase must close. |

### Required copy addition — the mod-tap sentence (closes success criterion 1 / Pitfall 3)

`SocdPanel.tsx`'s "What this does" notice currently states the layers rule and the macros
rule but has no mod-tap sentence. The underlying rule is already enforced structurally by
`validate.ts` (a directional position's base-layer binding must equal the exact expected SOCD
keycode — `binding.kind !== 'keycode' || binding.keycode !== expected` — which makes it
impossible for that position to simultaneously be a mod-tap). This is a documentation gap, not
a behavior gap: add one sentence, do not touch validation logic.

**Prescribed copy** (insert between the existing layers sentence and the existing macros
sentence, so the order reads layers → mod-taps → macros):

> "A position assigned to SOCD is bound to its SOCD keycode on the base layer, so it cannot
> also be a mod-tap — assigning one replaces the other."

Full paragraph after the edit:

```
{activePolicy ? activePolicy.description : 'Choose a policy to see how conflicts resolve.'}{' '}
Resolution applies to these four keys on the <strong>base layer only</strong>; on
other layers those positions behave normally. A position assigned to SOCD is bound to
its SOCD keycode on the base layer, so it cannot also be a mod-tap — assigning one
replaces the other. SOCD runs before macros, so a macro's own keypresses are never
altered.
```

No new CSS class, spacing value, or color is needed for this addition — it is plain text
inside the existing `.notice` block.

## UI Considerations

> Shape-rooted state coverage for this phase's UI surface, produced by the ui-consideration probe
> (`ui-consideration-probe.cjs`) at ui-phase step 9.5 and resolved interactively. Two elements are in
> scope: **E1** the SOCD config form (the fieldset in `SocdPanel.tsx`: enable checkbox, verified-policy
> select, directional-pair picker, four directional position selects) and **E2** the SOCD capability
> status copy (the "What this does" notice, the capabilities load-failure message, and the
> `CAPABILITY_UNAVAILABLE` reason string).
>
> Element kinds for E1 were authored as `form, interactive-control, static-content, list-collection`.
> The `list-collection` kind was added at the propose-then-confirm step because the verified-policy
> option set is variable-length and can legitimately be empty — the prose classifier missed it, and it
> is what raises the `populated` and `zero-one-many` rows below.
>
> Empty-state and error-state **copy** stays in `## Copywriting Contract`; this section covers state
> coverage and references those rows rather than restating them.

**Coverage:** 10 applicable · 10 resolved · 0 unresolved — 2 explicit, 2 backstop, 6 dismissed.

| Element | Category | Status | Resolution / Reason |
|---------|----------|--------|---------------------|
| E1 | empty | ✅ resolved (explicit) | When the verified-policy list for `(catalogVersion, keyboardId)` is empty on an otherwise SOCD-capable keyboard, `SocdPanel` renders the `CAPABILITY_UNAVAILABLE` `.notice` with its reason string; it never renders a policy `<select>` with zero options. |
| E1 | loading | ⊘ dismissed | No client-side loading state exists: capabilities, positions and keycodes arrive as props from a server-side fetch that completes before `SocdPanel` renders, the same shape as the rest of `KeymapEditorProps`. |
| E1 | error | 🧪 resolved (backstop) | An invalid SOCD selection (bad directional pair, wrong base-layer binding, position outside the layout) is rejected server-side by `validate.ts` with `CONFIG_INVALID` and field-level errors, surfaced through `KeymapEditor`'s `save.status === 'invalid'` → `fieldErrors` path. **Backstop:** no test yet asserts a SOCD-specific field error renders inside `SocdPanel` itself. |
| E1 | populated | ⊘ dismissed | The happy path renders exactly the registry-verified policy set returned by `listSocdCapabilities`; there is no volume-dependent layout concern, and the correctness of that set is covered by the `empty` and `zero-one-many` rows plus `REQ-socd-policy-choices` cl.1. |
| E1 | partial | 🧪 resolved (backstop) | Assigning one position to two directions is structurally impossible: `validate.ts` checks each direction's base-layer binding against that direction's expected SOCD keycode, and one position cannot equal two different keycodes. **Backstop:** no test explicitly names the duplicate-position-across-two-directions case. |
| E1 | overflow | ⊘ dismissed | No container can be exceeded: the panel's controls sit in a block-flow fieldset and `globals.css` declares no `max-height`, `overflow` or `white-space: nowrap` on `.socd`, `.socd fieldset` or `.notice`. |
| E1 | zero-one-many | ✅ resolved (explicit) | Zero verified policies routes to the `CAPABILITY_UNAVAILABLE` notice (see the `empty` row). Exactly one verified policy still renders the policy `<select>` as a select with a single option — never auto-selected and hidden — so "pick a policy from the verified list" stays literally true per success criterion 1. Many renders the same flat `<select>` with no grouping, pagination or truncation. |
| E1 | long-text | ⊘ dismissed | All copy in the form is short fixed strings (`SOCD_POLICIES` descriptions run to roughly 60 characters) rendered in wrapping block elements; no truncation or ellipsis handling applies. |
| E2 | overflow | ⊘ dismissed | `.notice` is a block element with default wrapping and no `max-height`, `overflow` or `nowrap` styling in `globals.css`, so long reason text wraps rather than clipping. |
| E2 | long-text | ⊘ dismissed | The longest string on this surface is the catalog-version-aware `CAPABILITY_UNAVAILABLE` reason at roughly 180 characters, which wraps normally inside `.notice`; no truncation or ellipsis handling is needed. |

### Lift into `must_haves` (plan-phase)

The planner MUST represent every resolved row below in a plan's `must_haves`. Explicit rows lift as
plain truth strings; backstop rows lift as flat-scalar markers (never a parenthetical — the verifier
branches on the `verification:` field). Dismissed rows do not lift.

```yaml
  - An empty verified-policy list for a SOCD-capable keyboard renders the CAPABILITY_UNAVAILABLE notice with its reason, never a zero-option policy select.

  - statement: A SOCD-specific CONFIG_INVALID field error renders inside SocdPanel on an invalid selection.

    verification: backstop
```
