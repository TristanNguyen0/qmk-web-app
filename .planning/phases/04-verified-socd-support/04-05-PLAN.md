<objective>
Prove on real hardware that the firmware this product builds applies the SOCD policy a user chose,
and record the evidence — the phase gate and the milestone success metric.

Purpose: ROADMAP criterion 4 and PROJECT.md's milestone success metric. Compiling is necessary and
not sufficient. `socd_resolve_test.c` already proves the resolution logic exhaustively on the host,
so the hardware run exists to prove wiring, keycode registration, flash fit, and QMK's real dispatch
order on a board the product has never touched (D-07).

Output: an artifact produced through the product path, a recorded hardware run, a registry that
claims exactly what was proven, and repository documentation that matches it.
</objective>

<task type="checkpoint:human-action" gate="blocking-human">
  <name>Task 2: Flash mode/m256wh and observe the policy on hardware</name>
  <action>
Flash the two firmware artifacts produced in Task 1 to the Mode Envoy (`mode/m256wh`) and observe
whether the chosen SOCD policy actually applies. This cannot be automated: the repository has no
flashing tooling and gains none in this phase (a deliberate scope decision), the board must be put
into its `stm32-dfu` bootloader by hand, and no emulator reproduces the USB HID timing of two
opposite keys pressed simultaneously.
  </action>
  <instructions>
For each of the two firmware files, one per policy:

1. Put the board into `stm32-dfu` bootloader mode and flash the file. Note which file you flashed
   and its SHA-256 before flashing, so the record names the exact image.
2. Open a key-event viewer or text field that shows what the board actually sends, then run the five
   checks from `04-VERIFICATION.md`:
   - Press W and S together and observe how the conflict resolves. For the neutral policy expect
     neither direction while both are held; for the last-input-priority policy expect the one
     pressed most recently.
   - With both held, release the first-pressed key and observe what is sent afterwards.
   - Repeat, releasing the second-pressed key instead.
   - Switch to the raised layer and press the same two physical positions; they must behave
     normally, because resolution applies on the base layer only.
   - Trigger the macro that types a direction key and confirm its own keypresses are not altered.
3. Record, per policy and per check: what you observed and whether it matched. Note any surprise
   verbatim rather than summarising it — a surprise here is the most valuable output of this phase.
4. Also note whether the firmware fit and flashed without a size or bootloader complaint.

If the board is unavailable this cycle, say so instead of approving. That path is planned for: D-09
requires the phase to stay open and the feature to ship as unavailable rather than as unproven.
  </instructions>

    stated that the hardware run cannot happen this cycle. A check reported without an observation,
    or an observation without a named firmware SHA-256, is not accepted.
  </verification>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| product path → user artifact | The firmware a user downloads is what gets flashed to their board |
| evidence record → product claim | The registry, README and ROADMAP make claims a user relies on |
| physical board → observation | The only place the end-to-end promise can actually be falsified |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-19 | Repudiation | a hardware claim with no evidence | high | mitigate | A record may carry hardware strength only when 04-VERIFICATION.md records a passing result for every check for both policies; the not-offered branch exists precisely so the alternative to evidence is withdrawal, not a weaker claim |
| T-04-20 | Tampering | the artifact between download and flash | medium | mitigate | The SHA-256 is recorded from the build record, re-computed over the downloaded bytes, and noted again before flashing, so the image that was observed is identifiable |
| T-04-21 | Spoofing | firmware presented as flashable after a failed build | medium | mitigate | Unchanged from Phase 3: a failed build has no artifact and returns a classified error; only a succeeded build yields a download |
| T-04-22 | Information Disclosure | build logs during the walkthrough | low | accept | Logs are redacted and capped, and served only to the owner; this plan adds no new log surface |
| T-04-SC | Tampering | the module bytes inside the flashed image | high | mitigate | The digest check runs before every materialization, so the image flashed corresponds to the reviewed module source and to the module version recorded on the build |
</threat_model>
